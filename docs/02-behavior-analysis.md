# 02 · 行为分析：它注册了哪些机制、具备哪些能力

本文全部内容来自**对归档二进制的静态分析**（只读）。因此它回答的是「**它能做什么**」，不是「**它此刻在做什么**」。

---

## 1. 核心机制：自保护三件套（驱动 `AliPaladinEx64.sys`）

在驱动二进制中直接搜到以下系统例程名（实测输出见 `evidence/driver-AliPaladin-functions.txt`）：

| 内嵌函数名 | 含义 | 直接影响 |
|---|---|---|
| `FltRegisterFilter` | 注册**文件系统微过滤器（minifilter）** | 可以拦截/放行文件操作 → **保护自己的安装目录**，删除时报 `Access denied` |
| `FltStartFiltering` | **启动**上述过滤器 | 与上一条构成完整的过滤器生命周期 |
| `CmRegisterCallback` | 注册**注册表回调** | 可以拦截注册表写入 → **把服务 `Start` 值改回 `auto`**（"禁用后几秒自己变回来"的机制解释） |
| `PsSetCreateProcessNotifyRoutine` | 注册**进程创建回调** | 可以感知进程创建/退出 → **守护 `AlibabaProtect.exe` 本体** |
| `KeStackAttachProcess` | **跨进程内存操作** | 可以读写其他进程的地址空间 |
| `IoCreateDevice` | 创建设备对象 | 提供**用户态通信接口** |

文件大小 177,880 字节。

**这就是"常规方法停不掉它"的完整技术解释**：三条回调各管一边 —— 文件（不让删）、注册表（不让禁用）、进程（不让杀）。三者都由同一个驱动注册，所以**只要驱动还在加载，清理就会被回滚**。

> 注意区分：`FltRegisterFilter` 说明它**能够**拦截文件操作，不等于它**正在**拦截所有文件操作。过滤器的具体规则需要额外证据（如 INF 里的 altitude、实际行为观察）。

### 1.1 独立第二证据：注册表侧的微过滤器配置

上表的"微过滤器"结论来自**驱动二进制里的代码串**。而在**服务注册表项**里，还有一组完全独立、指向同一结论的字段（实测值见 `evidence/service-AliPaladin-minifilter.txt`）：

| 字段 | 实测值 | 说明了什么 |
|---|---|---|
| `Group` | **`FSFilter Activity Monitor`** | `FSFilter` 是 Windows 为**文件系统过滤驱动**保留的服务组；`Activity Monitor` 子组按加载顺序处于链路**最上方** |
| `Altitude` | **`265109`** | 微过滤器的**唯一站位编号**，决定它在过滤栈中的确切位置；该值落在微软为"活动监视器类"预留的区间内 |
| `DependOnService` | **`FltMgr`** | 依赖**过滤器管理器**（Filter Manager）——这是微过滤器特有的加载机制，普通内核驱动不会依赖它 |
| `Type` / `Start` | `2` / `2` | 内核驱动 / 自动启动 |

**两套证据一致**：

```
代码侧（.sys 内嵌函数名）        注册表侧（服务配置）
──────────────────────────      ────────────────────────────────
FltRegisterFilter               Group = FSFilter Activity Monitor
FltStartFiltering               Altitude = 265109
                                DependOnService = FltMgr
```

⇒ 它是一个**已实际配置好站位、会被系统加载**的文件系统微过滤器，而不是"代码里出现过但没启用"的空洞能力。这直接解释了**"删除安装目录报 `Access denied`"**这一现象。

## 2. 用户态通信接口

| 观察 | 值 |
|---|---|
| 驱动导出的设备名 | **`\\.\CtrlSM`** |
| 驱动通信相关 API 出现次数 | 24（`CreateFileW` / `DeviceIoControl` / `NtDeviceIoControlFile` 等） |

`\\.\CtrlSM` 是 `AlibabaProtect.exe` 与内核驱动之间的**控制通道**。名字里的 `CtrlSM`（Control State Machine 或类似含义）与产品名无关联 —— 又一个"不要按名字判断"的例子。

**实操价值**：这个设备名可以用来确认"驱动是否在工作"。驱动未加载时，打开该设备会失败。

## 3. API 能力枚举

对安装目录中的主要可执行模块做字符串扫描（目标 27 个、实际命中 26 个），按类别统计命中的 API 名（**已剔除 DigiCert 等证书链噪声**）：

| 类别 | 命中数 | 说明 |
|---|---|---|
| **枚举类 API** | **61** | `SetupDi*` / `CM_*` / `EnumProcess*` / `CreateToolhelp32Snapshot` / `WTSEnumerate*` / `NetServerEnum` / `RegEnum*` / `FindFirstFile*` —— **设备、进程、会话、网络资源、注册表、文件**的枚举能力 |
| **网络上报 API** | **108** | `WinHttp*` / `InternetOpen*` / `HttpSend*` / `getaddrinfo` / `WSAStartup` 等 |
| **进程 / 内存 API** | **93** | `OpenProcess` / `ReadProcessMemory` / `Module32*` / `GetModuleFileName*` / `QueryFullProcessImageName*` / `ZwQuery*` |
| HTTP 头 / Content-Type 字面量 | 31 | `Content-Type` / `application/json` / `application/x-www-form-urlencoded` |
| 设备 / 枚举接口路径 | 26 | `\\.\` 开头的设备名 |
| **明文接口路径（`/api/...`）** | **0** | 见下方"重要发现" |
| 明文完整 URL | **1** | 且是第三方网站的链接 |

### 重要发现 1：**没有明文的上报接口**

预期会出现的 `/report`、`/collect`、`/upload` 之类的接口路径，**一条都没有**。而 HTTPS 所需的 `WinHttp*` 调用却有 108 处。

⇒ 结论只能是：**上报地址不以明文存放在二进制里**。它可能来自加密配置（见第 4 节）、运行时下发，或字符串加密。**这本身不构成任何指控，只是说明"静态分析看不到它的通信目标"** —— 这也正是第 5 节的边界所在。

### 重要发现 2：唯一的明文 URL 是一条技术论坛链接

唯一命中"完整 URL"的字符串是：

```
https://reverseengineering.stackexchange.com/questions/14171/thread-local-storage-access-on-...
   ← 出自 perfmonsdk.dll
```

一条**逆向工程论坛**的链接出现在 `perfmonsdk.dll`（性能监控 SDK，`1.2.68`）里，且内容是"线程局部存储访问"的技术讨论。

有两个解读，**都不指向恶意**：

1. 开发者把论坛讨论的代码片段直接复制进了工程，**连注释里的链接一起复制**了；
2. 该 SDK 引用了某段公开代码，链接是出处标注。

无论哪种，都说明 `perfmonsdk.dll` **至少部分基于公开代码/第三方片段** —— 这与它是"自研 SDK"的直觉不符。取证结论应记录为：**该模块的代码来源不完全是自研，存在公开代码引用痕迹**。

## 4. 配置与字符串被加密

### 4.1 `.dat` 配置文件不是文本

| 文件 | 大小 | 前 16 字节 |
|---|---|---|
| `AlibabaProtect.dat` | 942 B | `ff 10 10 ff 01 00 01 00 01 00 00 00 1e 03 00 00 ...` |
| `AlibabaProtectEx.dat` | 1,328 B | `ff 10 10 ff 01 00 01 00 01 00 00 00 a0 04 00 00 ...` |

用 `utf-8` / `utf-16-le` / `gbk` 三种编码尝试解码，**均为非文本**。

进一步观察：两文件在头部结构相同（`ff1010ff` 魔数 + 相同的字段区），随后是一串**明显的线性递增模式**：

```
... 00 84 08 8c 10 94 18 9c 20 a4 28 ac 2f b3 37 bb 3f c3 47 cb 4f d3 57 db 5f e2 66 ea 6e f2 76 fa 7e 02 86 ...
       ↑ 每项 +8，高位周期性进位
```

这种"**等步长递增**"是**按位运算或简易密钥变换**（逐字节 XOR / 加减）的典型特征，而不是强加密（强加密的输出应当近似随机）。

⇒ 结论：**配置文件经过轻量变换后存储**。也就是说，**它自己都不认为这些内容应当被轻易读到**。

> **未做也不打算做的事**：本仓库不解密、不提供解密方法。记录"内容被变换过"这一事实即可满足取证目的。

### 4.2 中文字符串被逐字节变换

对主进程与各 DLL 提取中文串时，**绝大多数输出是不可读的乱码**，例如：

```
佩赃耪魊 琵云耪魖
琵云琵ot$`排鬸勁踉团鹏zづ碓着汪j勁逶菖汪zづ菰缗汪jD琵耘琵o
砰哉派魖@篷韵霹ol$0派魊0霹云叛魖
```

但这些字符**并非随机**，而是呈现出高度一致的结构 —— 说明原文是中文，只是被按字节偏移了。

**同时，有两条字符串"漏网"了，是明文可读的**：

```
无法查询版本信息: 
无法获取当前进程的模块文件名: 
```

这两条是**错误提示文案**，厂家没有对它们做变换。它们恰好泄露了两个操作：

| 明文残留 | 可推出的操作 |
|---|---|
| `无法查询版本信息: ` | 会**查询版本信息** |
| `无法获取当前进程的模块文件名: ` | 会**获取当前进程的模块文件名** |

第二条特别值得记录：**一个常驻服务去获取"当前进程的模块文件名"，是自校验/自识别的典型动作**（确认"正在运行的是不是我自己的哪个副本"）。

> 这两条是**本次静态分析唯一直接看到的行为线索**。它们来自"漏网的明文"，而不是解密结果。

## 5. 结论边界：能力 ≠ 行为

本节必须明确一条分界线，否则容易把"能力清单"读成"罪行清单"。

| 已经证明的（**能力**） | 没有证明的（**行为**） |
|---|---|
| 驱动注册了文件/注册表/进程三类回调 | 它**实际上**拦截了哪些文件、哪些注册表键 |
| 具备完整的设备/进程/网络/注册表枚举能力 | 它**实际上**枚举了什么、多久一次 |
| 具备网络上报所需的完整 API 栈 | 它**实际上**往哪里发了什么数据（本机实测：**无 TCP 外连**） |
| 会获取当前进程模块名、会查询版本信息 | 它用这些信息**做了什么判断** |
| 配置与字符串被变换存储 | 变换算法是什么、配置里存了什么 |

**能做的与正在做的，中间隔着一条实测证据的鸿沟。** 本仓库把左侧写成表格，把右侧留白 —— 这是有意的。

## 6. 构建痕迹

| 线索 | 值 | 说明 |
|---|---|---|
| PDB / 构建路径 | `C:\jenkins\workspace\pc-sdk-build\...` | 使用 **Jenkins** 持续集成，工程名 **`pc-sdk-build`**（"PC SDK 构建"） |
| VC 运行时版本串 | `built by: REL AliSec` | 由**阿里安全团队**自行编译的 msvcp120/msvcr120 |
| 工程名与安装包名呼应 | 客户端目录下的安装包叫 **`pc-sdk-setup.exe`**（约 37 MB） | 与 CI 工程名 `pc-sdk-build` 对上 —— **证实这个安装包就是该 CI 工程的产物** |

**"CI 工程名"是一条高价值线索**：它把散落的文件（`pc-sdk-setup.exe`、驱动、DLL）串成同一条生产线，也说明了"为什么卸载客户端后它还会回来" —— 客户端的更新流程里包含了这个 SDK 的安装步骤。

## 7. 静态分析的局限（必读）

| 局限 | 后果 |
|---|---|
| 中文字符串与 `.dat` 均被变换 | **无法得到功能描述、配置内容、上报地址** |
| 未做反汇编 / 未做动态调试 | **无法确定控制流与判断逻辑** |
| 无网络抓包、无驱动 IOCTL 语义 | **无法确定 `\\.\CtrlSM` 的指令语义** |
| 无签名校验之外的完整性验证 | 无法排除"运行时会下载并执行额外代码"（本机实测无外连，但样本有限） |

**结论：静态分析能把"它注册了什么机制"说清楚，说不清"它打算做什么"。** 本仓库不越界。
