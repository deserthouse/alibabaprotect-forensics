# 03 · 资源开销实测

**简体中文** · [English](03-resource-cost.en.md)

清理的动机是"它在吃 CPU"。本文给出**实测数据、指标口径**，并对「**CPU 高的时候它在做什么**」给出诚实回答。

---

## 1. 实测数据

### 采样一（清理前，同一进程两个时间点）

| 指标 | 采样 A | 采样 B |
|---|---|---|
| 进程 | `AlibabaProtect.exe` | 同 |
| PID | 6108 | 6108 |
| 启动时间 | 09-21 17:21:49 | 09-21 17:21:49 |
| **累计 CPU 时间** | **4,875.5 s** | **5,077.5 s** |
| 工作集（内存） | 74.0 MB | 75.7 MB |
| 线程数 | 39 | 43 |
| 句柄数 | — | 968 |
| 采样时刻 | 09-22 00:07 | 09-22 00:23 |
| 父进程 | `services.exe`（由 SCM 拉起） | 同 |
| 命令行 | `"C:\Program Files (x86)\AlibabaProtect\1.0.70.3194\AlibabaProtect.exe"` | 同 |

### 指标口径：怎么从"累计秒数"算出"占用百分比"

累计 CPU 时间必须**除以进程运行时长**才能得到平均占用率：

```
运行时长 A = 09-22 00:07 − 09-21 17:21:49 = 6.75 h = 24,300 s
平均占用（单核）= 4,875.5 ÷ 24,300 ≈ 20.1 % 单核

运行时长 B = 09-22 00:23 − 09-21 17:21:49 = 7.02 h = 25,260 s
平均占用（单核）= 5,077.5 ÷ 25,260 ≈ 20.1 % 单核
```

**两个时间点独立算出同一个数（20.1%），说明这不是瞬时抖动，而是它的稳态行为。**

### ⚠️ 折算：单核百分比 ≠ 整机百分比

这台机器是 **16 逻辑处理器**：

```
整机占比 = 20.1 % ÷ 16 ≈ 1.26 %
```

**把"20% 单核"说成"吃掉五分之一台机器"是错的**（差 16 倍）。本仓库一律标注口径。

> 口径说明：以上是**累计值**折算的平均占用率，用于说明量级；用于跨进程比较时更严格的指标是**平均单核占用率**（即上式本身）。

## 2. 这份数据的局限（先说清楚再下结论）

| 局限 | 影响 |
|---|---|
| 只有**两个时间点**，无连续曲线 | 无法给出波动范围、无法排除"某段时间更猛" |
| 未捕获**峰值瞬时占用** | 用户主观感受到的"某次很卡"未被记录 |
| 未做**线程级**采样 | 只知道进程总耗时，不知道耗在哪个线程 |
| **单机数据** | 不同机器配置、不同版本行为可能不同 |
| 累计值受**开机时长**影响 | 已用平均占用率校正，见第 1 节 |

**这些局限不改变"它在稳定消耗约 20% 单核"这一结论，但意味着不能据此推断"它峰值能到多少"。**

## 3. 「CPU 高的时候，它到底在干什么」——诚实的回答

这是本仓库**唯一无法用现有证据回答**的问题。先把边界划清：

### 3.1 有直接证据的部分

| 事实 | 证据 |
|---|---|
| 它**不进行 TCP 外连** | 实测进程网络连接数 = **0** |
| 它有很多执行线程 | 39–43 线程 |
| 它持有大量内核对象 | 968 句柄 |
| 它有完整的"扫描类"模块 | `FileScanner.dll` / `FileWatch.dll` / `FileMonitor.dll` / `PathMon.dll` / `ProcessScanner.dll` / `HealthCheck.dll` / `Scheduler.dll` |
| 它有性能监控模块 | `perfmonsdk.dll`（`Perfmon` `1.2.68`） |
| 它会获取当前进程模块名、会查询版本信息 | 未加密的错误串残留（见 02.4.2） |

### 3.2 只能推测的部分（**标注为推测**）

把上面的事实拼起来，**最符合证据的推测**是：

> CPU 消耗来自**周期性巡检**——由 `Scheduler.dll` 调度，`FileScanner` / `PathMon` / `ProcessScanner` 执行枚举与校验，`perfmonsdk` 采集本地性能数据，`HealthCheck` 汇总。

**但这只是推测。** 理由：

1. **"有扫描模块"不等于"CPU 高时正在扫描"** —— 模块可能处于空闲。
2. 没有线程级栈采样，**没有任何一条证据把 CPU 时间归到某个具体函数**。
3. 配置文件与字符串被变换，**看不到调度周期、扫描范围、校验对象**。

### 3.3 想真正查清，需要这些手段

如果有人要接着往下挖，下面是能把"推测"变成"结论"的方法：

| 手段 | 命令 / 工具 | 能得到什么 |
|---|---|---|
| **CPU 栈采样** | `wpr -start cpu -filemode`（Windows Performance Recorder）→ WPA 打开 | **CPU 时间落在哪个模块/函数**（最能定论） |
| 实时线程栈 | Process Explorer → 进程属性 → Threads → Stack | 抓当前正在执行什么 |
| 文件/注册表活动 | Process Monitor，按进程名过滤 | 它**实际**在访问哪些路径、频率多高 |
| 驱动 IOCTL 语义 | 驱动侧 IOCTL 跟踪 | `\\.\CtrlSM` 指令含义 |
| 调度周期 | Procmon 时间戳间隔统计 | 巡检周期是几秒/几分钟 |

**结论：在拿到栈采样证据之前，"CPU 高时在干什么"应表述为"疑似与周期性巡检/自校验相关，未证实"。**

## 4. 为什么这对"要不要清理"的判断不重要

注意一个逻辑关系：

```
用户已经卸载了阿里系客户端
        ↓
用户不需要这个组件的功能
        ↓
于是"它到底在干什么"不再是决策前提
```

**判断依据不是"它做了什么坏事"，而是"我不需要它、它在消耗资源"。** 这条依据只需要第 1 节的实测数据就成立 —— 20% 单核、7 小时持续、且是被卸载客户端的遗留物。

把"未证实的行为"说成"已证实的危害"，既不符合证据原则，也会让整篇文档的可信度下降。**这是本仓库刻意保留的空白。**
