# 04 · 为什么删不干净

清理过程中会遇到的失败不是随机的，它们背后是**三条独立机制**。理解这三条，才能理解为什么"只删一次"没用。

---

## 1. 三条重新出现路径总览

| 路径 | 触发条件 | 实测证据 |
|---|---|---|
| **A. 回调自保护** | 服务/驱动仍在运行时，任何"禁用/结束/删除"操作被回滚 | 驱动内嵌 `FltRegisterFilter` + `CmRegisterCallback` + `PsSetCreateProcessNotifyRoutine`（见 02） |
| **B. SCM 自动恢复** | 服务崩溃或被杀后，由服务控制管理器按恢复策略重启 | 系统日志 **`7031`** 原文（见第 3 节）；**与是否有看门狗进程无关** |
| **C. 客户端重新安装** | 阿里系客户端（淘宝桌面版 / 阿里旺旺等）启动或更新时检查并重装 | 系统日志 **`7045`** 记录了同一驱动服务的**多次**安装；客户端目录内含 `SafeGuard\` 与 `pc-sdk-setup.exe` |

**路径 B 是最容易被忽略的一条。** 很多人杀掉进程后以为结束了，60 秒后它又回来了 —— 那不是"杀不干净"，是 SCM 按策略把它拉起来了。

---

## 2. 路径 A：回调自保护的表现

| 现象 | 机制解释（含置信度） |
|---|---|
| `sc config ... start= disabled` 后，几秒内 `Start` 变回 `2`（自动） | 实测观察到**回滚现象**；机制与驱动注册的注册表回调（`CmRegisterCallback`）能力**一致 —— 推断**。执行者未被逐一追踪（也可能是用户态进程轮询回写，如 `RestartService.exe`） |
| `Remove-Item` 安装目录报 `Access denied` | 文件系统微过滤器（`FltRegisterFilter`，注册表侧有独立配置证据，见 02）拦截了删除操作 |
| 结束进程后它自动回来 | 进程创建回调（`PsSetCreateProcessNotifyRoutine`）+ 路径 B |

### 实测到的具体失败与真相

| 操作 | 返回 | 真相 |
|---|---|---|
| `sc stop AlibabaProtect` | **1052**（请求的控件对此服务无效） | **正常现象**：该服务未实现停止处理逻辑，不是权限问题 |
| `sc delete AlibabaProtect` | 成功 | ✅ 服务注册项被标记删除，SCM 不再拉起；**进程本体不会因此终止**（实测：delete 后进程仍在，随后被显式结束，见 `evidence/cleanup-log.txt` 阶段 1c） |
| `sc stop AliPaladin` | 1062 / 1052 | **正常现象**：内核驱动在线不可停止 |
| 删除 `AliPaladinEx64.sys` 文件 | 报"安全删除"错误 | ⚠️ **假错误** —— 复查确认文件**已实际删除** |

> **"报错 ≠ 失败"** 这个坑值得单独记住：驱动文件删除时报错，但文件其实没了。清理后一定要**实际核验**（`Test-Path`），不要凭返回码下结论。

---

## 3. 路径 B：SCM 自动恢复（事件原文）

系统日志（`Service Control Manager`）中记录的原文：

```
[id=7031] Alibaba PC Safe Service 服务意外地终止，这种情况已经出现了 1 次。
          以下的修正操作将在 60000 毫秒内运行: 重新启动服务。
```

要点：

- **该恢复不依赖任何守护进程** —— 恢复动作由 SCM（服务控制管理器）执行，与该软件自己的进程是否存活无关，因此**只结束进程无效**。
- **应对只有一个：删除服务本身**（`sc delete`），而不是禁用或结束进程。服务注册项消失后，SCM 没有可重启的对象。
- 同类事件还有 `7034`（意外终止、无重启动作）、`7023`（因错误停止）—— 可用于还原崩溃历史。

### 3.1 独立第二证据：注册表里的 `FailureActions`

上面的 `7031` 是**运行日志**。同一份策略在**注册表**里也能看到（完整解码见 `evidence/service-failureactions.txt`）：

```
HKLM\SYSTEM\CurrentControlSet\Services\AlibabaProtect\FailureActions
  原始 44 字节，按 DWORD 解读：
  [ 0] 0            [ 1] 0            [ 2] 0            [ 3] 3
  [ 4] 20           [ 5] 1  ←SC_ACTION_RESTART          [ 6] 0xEA60 = 60000
  [ 7] 1  ←SC_ACTION_RESTART          [ 8] 0xEA60 = 60000
  [ 9] 1  ←SC_ACTION_RESTART          [10] 0xEA60 = 60000
```

| 从数据直接读出的 | 与日志的对应 |
|---|---|
| **3 次** `0xEA60 = 60000` 毫秒延迟 | 日志：`将在 60000 毫秒内运行` |
| **3 次** 数值 `1` = `SC_ACTION_RESTART`（重新启动服务） | 日志：`重新启动服务` |
| 前 3 个 DWORD 为 0（未设置重启提示与自定义命令） | — |

**两条相互独立的证据（注册表配置 + 运行日志）指向同一结论**，这是"关联≠因果"原则下最理想的情形：不是时间吻合，而是**同一件事在两个不同位置被记录下来**。

> 证据卫生：`FailureActions` 是 SCM 写入的二进制结构，不同 Windows 版本的头部字段布局可能有差异。上述表格只列**从数据本身能直接读出的**对应关系，不强行解释无法确证的偏移。完整原始值保留在 `evidence/service-AlibabaProtect.reg` 供复核。

## 4. 路径 C：重复安装的日志证据

`7045` 事件（"服务已安装在系统中"）保留了每一次服务安装的完整信息：

```
[id=7045] 服务已安装在系统中。
          服务名称: AliPaladin
          服务文件名: C:\WINDOWS\system32\drivers\AliPaladinEx64.sys
          服务类型: 内核模式驱动程序
          服务启动类型: 自动启动
```

**实测结果：这一个驱动服务，在 2026-07-11 至 2026-09-18 之间被记录了 `24` 次安装。**

```
2026-08-28 16:31:35
```

**平均约 3.5 天一次，且多次出现在同一分钟内成对出现**（`07-29`、`08-15`、`08-26`、`08-28`、`09-03`、`09-11` 各有一对）—— 说明这是**流程化的自动行为**，不是偶发。

这条证据的价值极高：**单看当前状态（服务已存在）根本发现不了"它会被反复安装 24 次"**。必须有安装历史才能看到这个模式。

> **证据卫生说明**：`evidence/scm-events.txt` 中还剔除了 **5 条本机排查实验中误建服务产生的 `7045` 事件**（服务文件名指向 `notepad.exe` / `blocked.exe`）。它们不是产品行为，混入会误导读者，因此单列在证据文件末尾并注明。

### "谁在装它"的三条线索

| 线索 | 具体内容 |
|---|---|
| 计划任务 | `AliProctectUpdate`、`AliUpdater`（注意前者是厂家的原始拼写，含 `Proctect` 拼写错误，非本文笔误） |
| 客户端目录内的安装器 | `SafeGuard\` 下的检查器与安装包；`pc-sdk-setup.exe`（约 37 MB，与 CI 工程名 `pc-sdk-build` 对应） |
| 更新器进程 | `AliProtectUpdate.exe`、`AlibabaProtectCon.exe` |

### 实测到的"复装"事件

**一次淘宝桌面版更新后，`AliUpdater` 计划任务被重新置为启用状态** —— 即：

> 客户端更新流程会把"检查并安装 AlibabaProtect"的自启项**重新打开**。清理时禁用的计划任务，会在下次客户端更新后被恢复。

⇒ 这直接证明：**一次性清理不足以维持干净状态**，需要"防复发"措施（见 06）。

### 半清理态实测：重新安装尝试被"文件缺失"阻断（第二台机器）

一台**只删了文件、未做任何拦截**（无 IFEO）的机器，`AliUpdater` 每小时仍运行一次，但每次尝试都失败：

| 观察 | 证据 |
|---|---|
| 更新器期望的版本目录不存在，每次在落地前失败 | `IntegrityCheck.ini` 明文错误 `[C:\Program Files (x86)\AlibabaProtect\1.0.70.988\] is not exist` |
| 尝试痕迹与任务时刻三重吻合 | 任务运行时刻 = `Logs\` 新增 ERROR 日志时刻 = `IntegrityCheck.ini` 改写时刻 |
| 尝试自清理（2026-03）持续至采集日（2026-09），**未停止、也未成功** | ERROR 日志按日计数；主程序 INFO 日志止于清理日，此后无成功运行记录 |

两点启示（完整数据见 `evidence/partial-cleanup-state.txt`）：

1. **"文件缺失"本身就是一道阻断** —— 重新安装路径 C 需要"安装器能落地"才成立；
2. **"没装回来" ≠ "没有在试"** —— 半清理状态会长期持续产生低噪声尝试痕迹。这也是 05 节"试了但进不来"判定的**另一条独立证据路径**（不依赖 IFEO / Prefetch）。

## 5. 一条只能标为"疑似"的观察

排查中还发现：`AliPaladin` 服务的 **`7000`（服务启动失败）事件全部集中在 09-21 的连续三次启动中**：

```
[id=7000] 由于下列错误，AliPaladin 服务启动失败: 连到系统上的设备没有发挥作用。
  └─ 2026-09-21 17:14:02
  └─ 2026-09-21 17:17:10
  └─ 2026-09-21 17:21:48
```

同一条错误（`连到系统上的设备没有发挥作用`）在 09-05、09-14 也各出现过一次 —— **共 5 次**。三次启动各自在约 20 秒内报同一条错误，说明**该驱动在那个时间窗口内持续无法正常初始化**。

**但这不能作为因果结论**，理由：

- 该时刻系统里同时加载着**大量内核驱动**，无法把崩溃单独归因到这一个
- "启动失败"也可能是崩溃重启的**结果**而非原因
- 时间接近 ≠ 因果

**正确表述**：`疑似相关，未证实；该驱动已被移除，此潜在因素随之消失。`

> **对照样本**：另一台机器上，`AliPaladin` 服务键**悬挂**（`Start=Auto` 但驱动文件已删）产生的 `7000` **可以直接归因**（43 条，2026-05 起，见 `evidence/partial-cleanup-state.txt` 第三节）。同样的错误号，归因条件完全不同 —— 这正是上表逐条列出"不能归因理由"的意义。

## 6. 正确的处置顺序（为什么是这个次序）

三条机制决定了**操作顺序不能乱**：

```
① 先禁用更新类计划任务
     └─ 防止清理过程中被"补装"

② 再 sc delete 服务（服务 + 驱动服务），随后显式结束进程
     └─ 断掉路径 B（SCM 自动恢复）
     └─ 注意：delete 只标记删除、不终止运行中的进程 —— 进程由 ③ 之前单独结束

③ 然后删文件与目录
     └─ 此时微过滤器已不再被加载，删除通常不再受阻

④ 必须重启
     └─ 内核驱动/过滤器只有重启才真正卸载
     └─ ⚠️ 启用"快速启动"时，"关机再开机"不会重建内核会话 —— 必须用「重启」

⑤ 重启后核验
     └─ 用 05 节的方法证明它没有回来
```

### 如果②③受阻：两阶段方案

若服务运行中拒绝一切修改，改用**两次重启**的迂回：

1. **第一阶段**：在服务仍运行时只做 `sc config AlibabaProtect start= disabled`
2. **重启**（此时它不会被拉起，进程与文件占用都消失）
3. **第二阶段**：重启后执行完整的 ②–⑤（通常不再受阻）

具体命令见配套的 [alibabaprotect-uninstall-guide](https://github.com/deserthouse/alibabaprotect-uninstall-guide)。
